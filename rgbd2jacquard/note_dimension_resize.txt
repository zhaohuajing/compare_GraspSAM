content height: 360 * 1.6 = 576 px
content region: y = 224 to 799

1024 x 1024

Its non-black content occupies approximately:

with black padding above and below. 

This is consistent with your converter script: it pads the original image to a square using side = max(h, w), then resizes the padded square to out_size x out_size. The script then applies this same square-resize function to RGB, mask, depth, and per-instance masks.

The correct intrinsics mapping should be letterbox-aware:

scale = 1024 / 640 = 1.6
pad_x = 0
pad_y = 224

fx_1024 = fx_640 * 1.6

cx_1024 = cx_640 * 1.6

The current (by 26/08/10) eval.py logic uses separate sx and sy, which would be wrong for this padded image because the image was not directly stretched from 640×360 to 1024×1024. It was padded to 640×640 first, then resized.

One important practical point: because your actual GraspSAM input is generated from a 640×360 RGB-D image, the cleanest parameter convention is to pass intrinsics corresponding to that same 640×360 image:

intr_w = 640
intr_h = 360
fx, fy, cx, cy = CameraInfo values for the 640x360 stream

If the only available CameraInfo is for the original 1280×720 color stream, you can either pass the original values with intr_w=1280, intr_h=720, or pass half-scaled intrinsics with intr_w=640, intr_h=360. These are equivalent only if the 640×360 image is produced by a simple 0.5 resize, not a crop.
